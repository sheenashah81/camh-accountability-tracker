Persistent instructions for Claude Code in this repository. Read this at the start of every session.

## Project
Independent portfolio replica of a CAMH (child and adolescent mental health) accountability tracker, inspired by a public MHPSS Design & Development Consultant Terms of Reference (TMC0007210). It is NOT affiliated with or endorsed by UNICEF or WHO. Data approach (decided 2026-10-21): real countries and real public indicators, each with a citation, source URL, licence check and "retrieved on" date. Commitments are included only where a public document supports them (source link + "verified on" date). Any extra records needed to demonstrate admin workflows must be clearly labelled "illustrative" in the data and on screen. Never invent commitments and attribute them to real governments as fact. Check each dataset's licence before adding it to the repo. Use original or appropriately licensed assets only. Never use real personal data, confidential information, official credentials or official logos. Starter countries: Kenya, Nigeria, South Africa, Bangladesh, Philippines, Colombia, Jordan, UK (an illustrative selection, not an official target list). Languages: English + Spanish (AI-assisted; reviewed by a person on 2026-11-01; new Spanish text is labelled "pending human review" until reviewed) plus a right-to-left placeholder layout test. Never claim connection to UNICEF, DevInfo or DHIS2 production systems, or production readiness.

The approved plan is at `~/.claude/plans/pasted-content-id-b93c-i-am-jazzy-wozniak.md` (phases 0–11, RTM, architecture, scope).

## Stack (decided)
Figma (design) · Drupal 11 via DDEV (site, admin, data) · Bootstrap 5 sub-theme · custom JS dashboard (ECharts + MapLibre) reading Drupal JSON:API · Behat + PHPUnit + axe/Pa11y · GitHub Actions. Power BI is a documented comparison only (Power BI Desktop is Windows-only, so it is not part of the build).

## Working conventions
- Work in small, reviewable steps: one task at a time, verified before the next.
- Keep `docs/rtm.md` (requirements traceability matrix) up to date as work progresses. Record limitations honestly, including which parts are simulated.
- Write all shareable material (README, docs, commit messages, comments) in a confident, professional voice.
- Prefer small, reviewable changes over large generated modules or themes.
- Identify missing information instead of inventing it.

## Git and GitHub
As you do work, commit to Git and push to GitHub regularly, with clean, meaningful commit messages, so we never lose the status or the work done.
- Commit after each completed task or logical checkpoint, not in large batches.
- Commit messages: short imperative summary line, then a line or two on why if useful.
- Push to GitHub after commits once a remote is configured (`git remote -v`). If no remote exists yet, tell the user and help them create one.
- Never commit secrets, credentials, `.env` files, or real personal data.

## Repository structure
